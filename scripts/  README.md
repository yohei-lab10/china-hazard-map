## 降雨強度(2026年8月改訂・10年分取得済み)

出典: CHIRPS(UCサンタバーバラ大学 Climate Hazards Center)。無料・APIキー不要。
中国気象局の暴雨分類基準(24時間降水量)でリスクに変換して使用。

### 何が変わったか

従来は「直近180日の最大値」という近似値だった。これは統計的な「何年に一度」の評価に
なっておらず、実行タイミング(季節)によって結果が変わるという問題があった。

新方式では、水文学で標準的な**年最大値法**を使う:
1. 過去10年分、各年の「年間最大24時間降水量」を1つずつ求める
2. その10個の年最大値に**Gumbel分布**をフィットする
3. 固定の再現期間(10年/50年/100年)それぞれに相当する降水量(mm)を逆算して表示する

出力GeoJSONにはGumbelパラメータ(`gumbel_mu`, `gumbel_beta`)が格納され、
再現期間の計算自体はブラウザ側(`index.html`)で行う。

### `risk`プロパティ(地図の色分けに使用)の算出基準

`rainfall_risk.geojson`の各地点には、再現期間計算用の`gumbel_mu`/`gumbel_beta`とは別に、
地図のWater Hazardヒートマップの色分けに直接使う`risk`(中国気象局の暴雨基準による
0/0.33/0.66/1.0の4段階分類)も格納されている。

**2026年8月に修正: 以前は「直近1年(2025年)の年最大値」のみで判定していた。**
これは180日近似値の時代から引き継いだ実装で、10年分のデータを取得した後も
そのまま残っていた。単年の値には強い年変動が乗るため、Gumbelパラメータ
(10年統計)と整合しない状態になっていた。実データで検証したところ、
1,661地点中329地点(19.8%)で1段階の分類ズレが生じていたことを確認している。

現在は`fetch_rainfall.py`側で **10年分の年最大値の平均** を暴雨基準に照らして
分類する方式に修正済み(`risk = rainfall_to_risk(float(np.mean(maxima)))`)。
年ごとのブレを均した「典型的な年最大降水量」を表す指標になっている。

### 現在のステータス: 10年分の取得完了(2026年8月)

2016〜2025年の10年分が完了し、全1,661地点で `years_used: 10` となっている
(418地点はCHIRPS範囲外等で `no_data`)。**再現期間の表示は稼働中。**

サーバー不安定のため1回では取り切れず、複数回に分けて実行して完走させた。
取得中は一部の日で `ConnectTimeout` が多発したが、年ごとの年最大値の中央値を比較したところ
各年とも全体比96〜111%に収まっており、**欠測による過小評価は生じていない**ことを確認済み。

今後、年次で最新年を追加する場合も同じ手順で実行すればよい
(既存の年はキャッシュ済みとしてスキップされ、不足年のみ取得される)。

### 画面表示(2026年8月に簡略化)

地点検索結果の降雨再現期間表示は、以下のようにシンプルな1〜2行に整理した:

```
10yr: ~119mm / 50yr: ~150mm / 100yr: ~163mm (10yrs data)
+1.5°C scenario (IPCC AR6, ~7%/°C)
```

- 外挿の不確実性注記(`*観測年数を大きく超える外挿のため...`)、観測基準の注記
  (`観測値(1981年以降のCHIRPS実測に基づく)`)、頻度の意味説明
  (`値はその量を超える頻度の目安...`)といった補足的な日本語注記は、
  画面が煩雑になるため削除した。技術的な注意点(外挿の不確実性、WMO推奨年数との差など)は
  本READMEと`china_hazard_map_manual_v3.pptx`(p.19)に引き続き記載している。
- 気候変動シナリオ(+1.5/+2/+3℃)選択時の説明文は英語に統一し、簡潔化した
  (`+1.5°C scenario (IPCC AR6, ~7%/°C)`)。
- 降雨再現期間・標高の周辺比較はいずれも**Water Hazardスコアの計算には使われない参考値**
  であることを明記する注記(`Reference only, not part of the Water Hazard score.`)を追加した。

### 取得作業の進め方

### 進捗の確認方法(重要)

**GitHub Actionsの「成功(緑チェック)」は完走を意味しない。**
スクリプトは、途中で打ち切られた場合でも「そこまでのデータでGeoJSONを生成して正常終了」する
設計になっているため、5年分しか取れていなくてもワークフローは成功と表示される。
実際に2026年8月の実行(#50)では、Actions上は成功だったが実際には5年分+2ヶ月しか
取得できていなかった。

**確実な確認方法は `data/rainfall_annual_max_cache.json` の `_progress` キーを見ること。**

```json
"_progress": {"2016": 12, "2017": 12, ..., "2021": 10}
```

年ごとに「何月まで完了したか」が記録されている。**全ての対象年が `12` になっていれば完走。**
上の例では2021年が`10`なので、次回実行時は2021年11月から再開される。

簡易的にはコミット履歴でも追える
(`chore: rainfall annual max cache — 2016年3月まで [auto]` のようなコミットが積まれる)。
**10年 × 12ヶ月 = 120コミットが完了地点。**

生成された `data/rainfall_risk.geojson` 側では、各地点の `years_used` プロパティで
実際に統計に使われた年数が分かる(未完了の年は除外されるため、5年分しか完了していなければ
`years_used: 5` となる)。この値は画面にも `based on Nyrs of data` として表示される。

**安全性**: 12ヶ月すべて揃った年のみがGumbelフィットに使われる。
途中までしか取得していない年の暫定値は自動的に除外されるため、
作業途中の中途半端なデータで再現期間を過小評価(危険側に誤る)することはない。
なお最低5年分揃わないとフィット自体が行われない。

### サーバー不調への対策(実装済み)

大量取得時に `Connection refused` / `ConnectTimeout` が頻発したため、以下を実装:
- **リトライなし**(`MAX_RETRIES = 1`)。失敗した日は即スキップ。
  1日欠けても年最大値への影響は軽微という割り切り
  (リトライ4回だと1日失敗ごとに35秒を消費し、1時間17分で1年目の9月までしか進まなかった)
- **接続タイムアウト15秒**(60秒から短縮)。応答しないサーバーを長く待たない
- **リクエスト間隔0.3秒**。サーバーへの負荷を抑える
- **50日連続失敗で中断**。繋がらない状態で数時間空振りするのを防ぐ

サーバーが不安定な時は無理せず、時間帯を変えて再実行するのが有効。
サーバーはカリフォルニア(UCSB)にあるため、現地の負荷が低い時間帯を狙う。

### 欠測率による年の自動除外(2026年8月追加)

サーバー不調時は「たまに成功、ほとんど失敗」という状態になり、
連続失敗カウント(`MAX_CONSECUTIVE_FAILURES`)ではこれを検出できない。
実際、2022年5〜6月(中国の雨季)がほぼ全滅したまま「12月まで完了」と
記録されかけた事例があった。

年最大値法は「その年で最も降った1日」を拾う手法なので、雨季が大量に欠測すると
年最大値を実際より小さく見積もり、**再現期間を過小評価(危険側に誤る)** してしまう
(NOAA GHCNdを不採用にした理由とまったく同じ問題)。

対策として、年ごとの取得成功率をキャッシュの `_coverage` キーに記録し、
`MIN_YEAR_COVERAGE`(既定90%)を下回る年は以下のように扱う:

- **統計から除外**(Gumbelフィットに使わない)
- **次回実行時に自動で再取得**(リセットして1月からやり直し。
  古い年最大値が残って混ざらないよう、該当年のデータを削除してから取り直す)

月ごとのログに `この年の取得成功率: 96% = 350/365日` と表示されるので、
実行中も品質を確認できる。

**注意**: 現在リポジトリにある2016〜2025年のデータは、この仕組みを追加する前に
取得したものなので `_coverage` の記録がない。記録のない年は判定材料がないため
無条件に採用される(後方互換)。上記の通り年最大値の分布を検証して品質に問題が
ないことは確認済みだが、厳密に揃えたい場合は該当年の `_progress` を削除して
取り直す必要がある。

### 他のデータ経路の調査結果(2026年8月に実地検証)

CHIRPS直接取得が難航したため代替経路を検証したが、いずれも不採用。
詳細な検証結果は `china_hazard_map_manual_v3.pptx` の p.20 を参照。

| 経路 | 結果 | 理由 |
|---|---|---|
| IRI Data Library | **使用不可** | 2026年8月時点で全ユーザーにサインイン必須化。未ログインだと全て`-9999`(欠測)のファイルが返る |
| NOAA NCEI (GHCNd) | **不適** | APIは正常動作するが地上観測所の点データ。南京(CHM00058238)の2016年7月は31日中20日(65%)が欠測。年最大値を見逃すと再現期間を過小評価するため不採用 |
| CHIRPS (FTP) | 未検証 | 同一サーバーのため同じ制限を受ける可能性が高い。`requests`がFTP非対応で実装変更も必要 |
| Google Earth Engine | 次善策として保留 | `UCSB-CHG/CHIRPS/DAILY`。サービスアカウントで自動化可能だが、認証設定の手間と中国国内から利用できない制約あり |

### 注意事項

- CHIRPSは北緯50度〜南緯50度のみカバー。それより北(黒竜江省北端の一部)はデータ欠損として扱われ、
  地点検索パネルに"No data"と表示される
- 10年はWMOガイドラインの推奨(20〜30年)に届かない妥協値。
  50年・100年の再現期間は観測年数の5〜10倍の外挿にあたり不確実性は大きいが、
  画面表示は簡潔さを優先し警告注記は省略している(2026年8月)。技術的な注意点は本項目に記載の通り
- 実行時間の目安: サーバーが安定していれば1日あたり約1.3秒、10年分(3,650日)で約1.6時間
  (実測根拠: 180日版が3分51秒で完走した #39 の実績)

1. GitHubの「Actions」タブ →「Update Hazard Data」→「Run workflow」
2. `run_rainfall` にチェックを入れて実行
3. 完走しなかった場合は、日を改めて同じ手順を繰り返す(前回の続きから再開される)

### 方法B: ローカルで実行

```
pip install rasterio requests numpy
python scripts/fetch_rainfall.py --years 10 --grid-deg 1.0 --out data/rainfall_risk.geojson --cache data/rainfall_annual_max_cache.json
```

ローカルで完走させた場合は、生成された `rainfall_risk.geojson` と
`rainfall_annual_max_cache.json` の両方をコミットすること。

## 気候変動シナリオの切替(2026年8月実装)

地点検索の再現期間表示には、**Current / +1.5°C / +2°C / +3°C** を切り替えるラジオボタンがある
(Aqueduct Floodsの10年/100年切替と同じ操作感)。

### なぜ必要か

Gumbel分布は「降水量の統計的性質は時間によって変わらない」という**定常性**を前提としている。
気候変動で極端降水が増加傾向にある場合、この前提は崩れており、将来のリスクを過小評価しうる。

本来は非定常GEV(パラメータを時間の関数にする)で扱うべきだが、
**10年分のデータではトレンドを検出する統計的検出力が無い**(気候トレンドの検出には通常30年以上必要)。
そのため、IPCCの知見に基づく係数を掛ける実務的な方式を採用した。

### 根拠と計算式

**IPCC AR6 第11章**: 年最大日降水量(Rx1day)の変化は世界平均地上気温の変化に比例し、
Clausius-Clapeyron関係に従って**1°Cの昇温あたり約7%増加**する(観測・将来予測とも)。
中国域の研究でも日降水量の極値は6〜7%/°Cとほぼ同じ関係が報告されている。

```
係数 = 1 + 0.07 × 昇温℃
表示値 = Gumbelから算出した降水量 × 係数
```

**この方式を選んだ決め手**: IPCCが示す指標が`Rx1day`(年最大日降水量)であり、
本サイトが算出しているものと**指標が完全に一致している**こと。

### 実装上の注意

- 係数は `index.html` の `RAINFALL_CC_PCT_PER_DEG`(既定7)と
  `RAINFALL_WARMING_SCENARIOS`(既定 `[0, 1.5, 2, 3]`)で変更できる
- 切替時に通信は発生しない(Gumbelパラメータから即座に再計算するため)
- 画面上の説明文は2026年8月に英語へ統一・簡潔化した
  (例: `+1.5°C scenario (IPCC AR6, ~7%/°C)`)。「到達時期を示すものではない」という
  補足は画面からは省略し、本READMEおよびPPT(p.19)に記載する形に整理した
- Currentを選ぶと係数1.0となり、純粋な観測ベースの値になる

## 統合レポート機能(2026年8月実装)

ヘッダーの「REPORTS」ボタン(どのハザードタブを選択中でも常に表示)から、
複数拠点の地震・台風・雷・水害を1つのPDFにまとめて出力できる。
保険会社の社員が地点を入力し、生成したPDFを契約者に手交する運用を想定した機能。

### 使い方

1. ヘッダーの「REPORTS」ボタンをタップすると地点入力パネルが開く
2. 座標系(WGS84 / GCJ-02 / BD-09)を選択
3. 物件名(任意)・緯度・経度を入力。「+ Add location」で複数拠点を追加可能
4. 「Generate integrated report」でPDFを直接ダウンロード
   (ブラウザの印刷プレビュー画面は経由しない)

**Location 1の自動入力(2026年8月追加)**: 通常の地点検索(画面上部の緯度経度入力+Locate)で
既に座標を検索済みの場合、Location 1の緯度・経度欄に自動でコピーされる。
「REPORTSボタンを先に開いてから地点検索する」「地点検索を先にしてからREPORTSボタンを開く」
のどちらの順番でも反映される(`syncReportLocationFromSearch()`が地点検索のたびと、
REPORTSボタンを開くたびの両方で呼ばれる設計)。ただし対象はLocation 1が1件だけ・
まだ未入力の場合に限られ、既に入力・編集済みの内容や、2件目以降のLocationは上書きしない。

### レポートの構成

地点ごとに1ページ(改ページなしで縦長の1枚に収める)。各ページの内容は
**地震 → 台風 → 雷 → 水害** の順の4セクション:

- 各セクション共通: ▽マーカー付きのリスク凡例バー、バッジ、1行の説明文
  (台風のみCategory1+の発生頻度も追記)
- 水害セクションのみ追加で表示:
  - 降雨再現期間: ブラウザの地点検索と同じ文言(`10yr: ~119mm / ...`)に加え、
    Current/+1.5/+2/+3℃の4シナリオを重ねた曲線グラフ(Chart.js)
  - 標高3D地形: 中心+周囲8方向(実測9点、半径100m)をそのまま3×3グリッド化した
    3D曲面(Plotly.js)。補間はしていないため、モックアップ段階で見せた滑らかな地形図より
    やや角ばった見た目になる。距離軸(E–W/N–S、±100m)とカラーバー(青=低い/赤=高い)を表示。
    中心(検索地点、座標0,0)には黒いダイヤモンド型マーカー+「Search point」ラベルを
    地表面から少し浮かせて表示し(標高差の15%または最低1m)、地形に埋もれず
    どこが検索地点かひと目でわかるようにしている(2026年8月追加)
- ページ末尾に「本レポートは参考情報であり、保険引受の唯一の根拠として使用しないこと」
  という趣旨の免責文言を固定表示

### 技術的な実装メモ

- **既存のハザード判定ロジックを再利用**: `earthquakeRiskInfo` / `typhoonRiskInfo` /
  `lightningRiskInfo` / 水害の合成ロジックなど、通常の地点検索(`queryPoint`)が使っている
  関数をそのまま呼び出す`computeReportData(lat, lon)`を新設。`activeLayers`(画面上で
  選択中のハザードタブ)には依存せず、レポートでは常に4種類全てを計算する
- **PDF生成方式**: 当初は`window.print()`(ブラウザの印刷機能)を使う設計だったが、
  以下の問題が判明したため`html2canvas` + `jsPDF`による直接ダウンロード方式に変更した:
  - 印刷プレビュー画面を経由してしまい、「PDF出力ボタン」としての体験に合わない
  - 内容が長いと複数ページに分割されてしまい、「地点ごとに1枚」の要件を満たせない
    (jsPDF側でページ高さをコンテンツ量に応じて可変にすることで解消)
- **Plotly(3D地形図)が印刷/キャプチャで消える問題**: PlotlyのsurfaceプロットはWebGL
  キャンバスを使うが、WebGLは描画後にバッファがクリアされる仕様のため、ブラウザ印刷や
  `html2canvas`による再キャプチャの時点では空(透明)になってしまうことがある。
  対策として、`Plotly.newPlot()`完了後に`Plotly.toImage()`でPNG画像化し、
  元のPlotly描画領域を`<img>`タグに差し替えてから`html2canvas`でキャプチャする方式にした
- Chart.js側も`responsive:false`にしてcanvasサイズを固定し、`animation.onComplete`で
  描画完了を待ってから次の処理(PDF化)に進むようにしている
- レポート用のDOM(`#reportView`)は、`display:none`だとレイアウト計算やcanvas/WebGL描画が
  行われず`html2canvas`が空キャプチャしてしまうため、`position:fixed; left:-99999px`で
  画面外に配置する方式にしている(存在はするが目には見えない)
- Chart.js / Plotly.js / html2canvas / jsPDF はいずれもCDNから遅延読み込み
  (レポート生成ボタンを押した時点で初めて読み込む。通常の地図閲覧時の初期読み込みには含めない)

## 地震ハザードの算出基準(2026年8月修正)

出典: USGS Earthquake Catalog API。M5.0以上、50年分バックフィル後は日次差分更新。

### マグニチュード正規化のバグ修正

`earthquakeRiskInfo()`は、周辺100km以内の地震について「マグニチュード×震源距離」の
実効値(`effective`)を計算し、5段階に配色している。

```
falloff  = max(0, 1 - 距離km / 100)                    // 距離0km=1.0、100km=0.0
magRatio = 旧: min(1, max(0, (M - 5.0) / 2.5))          // 線形、M5.0=0.0
effective = magRatio × falloff
```

**問題**: マグニチュード正規化が線形かつM5.0を起点0.0としていたため、震源距離が0km
(真上)であっても、ちょうどM5.0の地震は`magRatio=0`となり、`effective`が必ず0になって
いた。地図のバッジ文言は「M5.0+ earthquake」だが、実装上はM5.0そのものが実質的に
評価対象から漏れる、という文言と実装の矛盾があった。

**修正**: マグニチュード正規化を2乗カーブ化し、下限を設けた。

```javascript
const magRatioLinear = Math.min(1, Math.max(0, (mag - 5.0) / 2.5));
const magRatio = Math.max(0.05, Math.pow(magRatioLinear, 2));
```

| マグニチュード | 旧(線形) | 新(2乗+下限) |
|---|---|---|
| M5.0 | 0.00 | 0.05 |
| M5.5 | 0.20 | 0.05(下限にクリップ) |
| M6.0 | 0.40 | 0.16 |
| M6.5 | 0.60 | 0.36 |
| M7.0 | 0.80 | 0.64 |

副次効果として、地震のエネルギーが指数的に増加する(マグニチュード1につき約31.6倍)

## 台風ハザードの算出基準(2026年8月修正・その2)

出典: IBTrACS(NOAA/WMO)。6時間おきの観測点(緯度経度・風速・暴風域半径r34_km)を
台風ごとに時系列で保持している。

### 観測点"間"が未評価だった問題

`estimateStormWindAt()`は、地点検索・地図タイルの両方で、指定座標での推定風速(kt)を
求めるために使われている。これまでは台風の**観測点(6時間おきの記録)そのもの**でしか
評価しておらず、地図上に描画される観測点間の直線区間の"途中"は一切評価されていなかった。

台風は6時間で100〜300km移動することもあるため、観測点間隔が広い区間では、地図上の
台風経路(直線)にかなり近い、あるいは線の真上であっても、両端の観測点どちらの暴風域
半径からも外れていれば「Category1+の影響なし」と判定されてしまう問題があった。

### 修正: 区間(2点間)を線分として評価

観測点iと観測点i+1を結ぶ区間について、指定地点から**線分上の最近接点までの距離**を
計算し、その位置(区間内の割合t)での風速・暴風域半径を両端から線形補間して評価する
方式に拡張した。

```javascript
// 局所平面近似で線分上の最近接点までの距離とtを求める
function closestPointOnSegmentKm(lat, lon, lat1, lon1, lat2, lon2) { ... }

// 区間の両端(w1, w2 / r34_1, r34_2)をtで線形補間してから、
// 「中心=補間後の風速、r34地点=34kt」の減衰を適用
const wT = w1 + t * (w2 - w1);
const r34T = r341 + t * (r342 - r341);
if (distKm <= r34T) est = 34 + (wT - 34) * (1 - distKm / r34T);
```

t=0で観測点iそのもの、t=1で観測点i+1そのものと一致するため、従来の観測点ベースの
判定を包含する形の拡張になっている(観測点そのものでの評価コードも、フォールバック
として残してある)。

**近似精度について**: 緯度経度を局所的に平面近似している(観測点間隔は最大でも数百km
程度のため、この範囲では十分な精度)。厳密な測地線(大圏)上の最近接点計算ではない。

## 台風ハザードの地図描画変更(2026年8月修正・その3)

### 「線に近ければ危険」という誤解

これまで地図上の台風経路は、太さ固定(`weight: 5`)の単純な線として描画していた。
しかし実際の暴風域半径(r34_km)は台風によって11〜581km(中央値185km)と大きく
ばらつくため、線の見た目の太さと実際の暴風域の広さが全く連動しておらず、
「線に近ければ危険」という誤解を招きやすい状態だった。地点検索側は既にr34を
考慮した判定をしているのに、地図の見た目だけがそれを反映していなかった。

### 修正: r34幅の帯(半透明ポリゴン)として描画

各区間(観測点i・i+1間)について、進行方向に直交する向きに、両端それぞれの
r34_km分だけオフセットした4点を求め、台形状のポリゴンとして描画するよう変更した。

```javascript
const brg = bearingDeg(a.lat, a.lon, b.lat, b.lon);        // 区間の進行方向
const perpL = brg - 90, perpR = brg + 90;                   // 直交する2方向
const aL = destinationPoint(a.lat, a.lon, perpL, a.r34);     // 大圏航路で正確にオフセット
const aR = destinationPoint(a.lat, a.lon, perpR, a.r34);
// b側も同様に求め、[aL, bL, bR, aR]の4点でポリゴンを描画
```

r34欠損時は、地点検索(`estimateStormWindAt`)と同じフォールバック半径
(`TYPHOON_FALLBACK_RADIUS_KM` = 200km)を使い、表示と判定の基準を一致させている。

帯同士が重なっても地図が見えなくなりすぎないよう、`fillOpacity: 0.28`と
透過度を上げて半透明にした。

## 台風の発生頻度による重み(2026年8月実装・改訂その4)

### 課題: 「1回の強烈なCategory5」と「繰り返すCategory1」が区別できなかった

`typhoonRiskInfo()`(地図の色・地点検索バッジ)は、これまで過去最も強かった**1回の
イベント**の風速のみで判定しており、頻度は`typhoonReturnPeriodInfo()`で別途計算して
補足テキストとして表示するのみで、色・ティアには一切反映されていなかった。

### 実装: 水害の洪水実績重みと同じ設計

```javascript
const TYPHOON_FREQ_WEIGHT_N = 5;  // 経験則的な調整値。実データを見ながら今後調整
function typhoonFrequencyWeightAt(lat, lon) {
  const ev = typhoonCategory1PlusEvents(lat, lon);  // データ期間全体でのCategory1+発生回数
  if (!ev || ev.totalEvents === 0) return { weight: 1.0, ... };
  const relative = Math.min(1, ev.totalEvents / TYPHOON_FREQ_WEIGHT_N);
  return { weight: 1 + 0.5 * relative, ... };  // 1.0〜1.5倍
}
```

`typhoonRiskInfo()`は、単発最大強度のratioにこの重みを掛け、`min(1, ...)`で0〜1に
収めてからtierを再計算する。水害ハザードの`floodWeightAt()`(1 + 0.5 × 相対値、
1.0〜1.5倍、下限1.0固定)と全く同じ設計思想。

| 過去の発生回数(データ期間内) | weight |
|---|---|
| 0回 | 1.00倍 |
| 1回 | 1.10倍 |
| 3回 | 1.30倍 |
| 5回以上 | 1.50倍(頭打ち) |

N=5は水害の80km・0.5係数と同様、公式基準ではなく経験則的な調整値。まずはこの値で
試験導入し、実データでの発生回数の分布を見ながら調整する方針。

`typhoonReturnPeriodInfo()`との重複計算を避けるため、Category1+発生回数のカウント
ロジックは`typhoonCategory1PlusEvents()`という共通ヘルパーに切り出した。

## 台風の帯の幅がr34と一致していなかった問題(2026年8月修正・改訂その5)

### 発見の経緯

改訂その3でr34幅の帯を実装した後、地点検索では「Category1+ impact なし」なのに、
その地点が真っ赤な(High/Severe相当の)帯の中にある、という矛盾が実地検証で見つかった。

### 原因: r34(34kt到達点)とCategory1(64kt以上)を混同していた

`r34_km`は「34kt(トロピカルストーム相当)が届く範囲」の半径であり、Category1の
基準(64kt以上)とは全く別の閾値。台風の風は中心から離れるほど弱まるため、
r34の範囲の中でも、外側は34kt程度(Category1未満)にしかならない。

```
中心(最強) ●━━━━━━━━━━━━━━━━━━━━━━━━━━━● r34の端(34kt)
            ↑ここだけ実際は64kt以上          ↑ここは34kt程度
            (本来のCategory1+範囲)
```

改訂その3の実装は、r34の幅をそのままCategory1+の色で塗ってしまっていたため、
実際には34〜63ktしかない外側のエリアまでHigh/Severe相当として表示されていた。

### 修正: 「実際に64ktに達する距離」を逆算

`estimateStormWindAt`と同じ減衰式(中心=w、r34地点=34kt、線形補間)を逆算し、
帯の幅にはr34ではなく、この「Category1到達距離」を使うようにした。

```javascript
// 減衰式: wind(d) = 34 + (w - 34) × (1 - d / r34)
// wind(d) = 64 について d を解く:
function category1RadiusKm(w, r34, hasR34) {
  const CAT1_KT = TYPHOON_CATEGORY_BOUNDS_KT[0]; // 64
  if (typeof w !== 'number') return 0;
  if (!hasR34) return w >= CAT1_KT ? TYPHOON_FALLBACK_RADIUS_KM : 0;
  if (w <= 34) return 0;
  const d = r34 * (1 - (CAT1_KT - 34) / (w - 34));
  return Math.max(0, Math.min(r34, d));
}
```

r34欠損時(フォールバック)は距離減衰が無い(200km以内は一律w)前提のため、
w≥64ktなら200km、それ未満なら0という単純な二値になる。

**検証**: 逆算した距離を元の減衰式に代入すると、ちょうど64.00ktになることを確認
(w=134kt, r34=150km → 距離105.0km → windAtDist(105.0) = 64.00kt)。これにより、
地図の帯と地点検索の判定が完全に一致するようになった。

## 台風: 地点検索とレンダリングのモデル統一(2026年8月修正・改訂その6/その7)

### 改訂その6: 片方の観測点にwinds_ktが欠損している区間のスキップ漏れ

`estimateStormWindAt()`の区間評価は、以前は両端に有効な`winds_kt`が揃っている区間
だけを評価しており、片方が欠損している区間は丸ごとスキップしていた。一方、描画側
(`collectTyphoonSegments`)は片方だけでもその値で区間を描画するため、「地図には
帯が見えるのに、区間の途中は地点検索で一切評価されない」という不整合があった。

### 改訂その7: そもそも地点検索とレンダリングで前提モデルが違っていた(根本修正)

改訂その6の個別修正後も、実地検証で新たな不一致が見つかった。原因を調べたところ、
より根本的な設計の不一致に気づいた:

- **レンダリング**(`collectTyphoonSegments`): 区間ごとに「一定の帯」として描画。
  帯の幅はCategory1到達距離(`category1RadiusKm`)を区間の両端で線形補間したもの
- **地点検索**(改訂その6までの`estimateStormWindAt`): 距離に応じて連続的に
  減衰する「中心=w、r34地点=34kt」のモデルを使用

この2つは前提となる数理モデルそのものが異なっており、個別の不整合(観測点欠損の
扱いなど)を直すたびに、また別の不一致が発生する構造だった。

**修正**: 地点検索側も`category1RadiusKm()`による「区間の帯の中にいるかどうか」
判定に統一した。

```javascript
// 各観測点のCategory1到達半径(レンダリングと完全に同じ計算)
const catRadii = coords.map(([, ], i) => {
  const w = windsKt?.[i] ?? null;
  const hasR34 = !!(r34Km && typeof r34Km[i] === 'number' && r34Km[i] > 0);
  const r34raw = hasR34 ? r34Km[i] : TYPHOON_FALLBACK_RADIUS_KM;
  return { w, catR: category1RadiusKm(w, r34raw, hasR34) };
});

// 区間ごと: 両端のcatRadiusをtで線形補間した「帯の幅」の中にいるかどうかで判定
const catT = p1.catR + t * (p2.catR - p1.catR);
if (distKm > catT) continue; // 帯の外
```

**検証**: 観測点0(風速90kt、r34=120km)から観測点1(風速データ欠損)への区間で、
観測点0からの距離を変えてテストしたところ、`category1RadiusKm(90, 120, true)`が
返す境界距離(約55.7km)のすぐ内側では風速90ktが返り、境界を超えると`null`
(Category1+ impactなし)に切り替わることを確認した。これにより、地図の帯と
地点検索の判定が、近似誤差ではなくロジックレベルで完全に一致するようになった。

## 台風: JMA(気象庁)基準への切り替え(2026年8月修正・改訂その8)

### 発見: データがJMA方式(10分間平均)だった

実際の`typhoons.geojson`をTyphoon Meranti(2016年、観測史上最強クラス)の記録と照合:

| | このデータの`max_wind_kt` | 実際の発表値 |
|---|---|---|
| データの値 | 120.0kt | — |
| JMA(気象庁)発表 | — | 220km/h ≈ 118.8kt(10分間平均) ← ほぼ一致 |
| JTWC(米軍)発表 | — | 315km/h ≈ 170kt(1分間平均) ← 大きく乖離 |

このサイトの`winds_kt`はJMA方式(10分間平均)であることが確定した。以前使用していた
Saffir-Simpson基準(64/83/96/114/136kt)は米国JTWC方式(1分間平均)を前提に設計された
基準であり、同じ台風でも1分間平均は10分間平均よりおよそ12〜14%高く出るため、
JMA方式の数値をそのまま当てはめると実際の強さを系統的に過小評価してしまう
(Merantiの例: 120kt→旧基準ではCategory4止まり、1分間平均換算では約137ktでCategory5相当)。

### 修正: JMA自身の階級基準に変更

データの出典(JMA)に合わせ、JMA公式の4階級・kt換算値に切り替えた。

```javascript
// 17.2m/s(台風)・33m/s(強い台風)・44m/s(非常に強い台風)・54m/s(猛烈な台風)をkt換算
const TYPHOON_CATEGORY_BOUNDS_KT = [34, 64, 85, 105];
const TYPHOON_TIER_COLORS = ['#D9A22C', '#D9722C', '#C13A2E', '#1A2130'];
const TYPHOON_TIER_LABELS = ['Typhoon', 'Strong Typhoon', 'Very Strong Typhoon', 'Violent Typhoon'];
```

**表示範囲の変更**: 最低ラインをJMA基準に完全一致させ、34kt以上(JMA「台風」全体)を
表示するよう変更した。以前は64kt未満(Saffir-Simpson Category1未満)を一律「対象外」
としていたため、これまで地図に出ていなかった弱めの台風も新たに表示されるようになる。

**色分けの段階数**: 他のハザード(地震・水害など)と共有していた5段階
(`WARNING_TIER_COLORS`、Low/Moderate/High/Severe/Extreme)から独立させ、台風専用の
JMA4段階(`TYPHOON_TIER_COLORS`/`TYPHOON_TIER_LABELS`)に変更した。バッジの凡例
(`riskLegendHtml`)は`labels`引数を新設して対応し、他のハザードは従来通り5段階の
まま影響を受けない。

**副次的な単純化**: 最低閾値がr34_kmの定義(34kt到達半径)そのものと一致したため、
`category1RadiusKm()`(→`typhoonReachRadiusKm()`に改名)の減衰式は、最低閾値の場合に
`d = r34 × 1 = r34`となり、実質的に距離補間が不要になった(汎用性は保持したまま)。

### 検証

Meranti(120kt)を新基準に通すと正しく「Violent Typhoon」(tier=3、猛烈な台風相当)と
判定されることを確認した(旧基準ではCategory4止まりだった)。

## ローリングウィンドウ→開始年固定への変更(2026年8月修正・改訂その9)

### 問題: 古い年がGumbel計算から静かに脱落していた

`fetch_rainfall.py`は、`--years`(既定20)を使って「直近N年」のローリングウィンドウで
対象年を決めていた。

```python
target_years = list(range(today.year - args.years, today.year))
```

このため、来年再実行すると対象年が1年分スライドし、最も古い年(例: 2016年)が

宙に浮いたデータになっていた。実害(誤った計算結果)はなかったが、ファイルが
年々肥大化する一方で、観測年数は10年のまま増えないという設計だった。

### 修正: 開始年(2016)固定、年々データが増える方式に変更

```python
START_YEAR = 2016  # このデータセットの取得を開始した年。変更しない。
target_years = list(range(START_YEAR, today.year))
```

`--years`引数は「初回実行時に何年遡るか」という意味に位置づけ直し、2回目以降は
`START_YEAR`固定により実質無視される。

**検証**: 2026年実行時は2016〜2025年(10年分)、2027年実行時は2016〜2026年
(11年分)となり、2016年のデータは2027年時点でも対象に含まれ続けることを確認した。

**副次的な利点**: 観測期間が長くなるほど、50年・100年といった再現期間の外挿倍率

永遠に10年のままだったが、この変更により年々WMO推奨に近づいていく。

## ワークフローファイル(update-data.yml)との突き合わせで発見した問題(2026年8月修正)


ところが実際の`update-data.yml`は、今も明示的に`--years 10`を渡していた:

```yaml
run: python scripts/fetch_typhoons.py --years 10 --out data/typhoons.geojson
```

このため`args.years`が常に`10`(truthy)になり、**修正した固定開始日ロジックが一度も
実行されず、旧ローリングウィンドウのままだった**。降雨側は`args.years`自体を
`target_years`の計算に使わない設計にしていたため同じ問題は起きなかったが、
台風側は作り方の違いにより、ワークフローとスクリプトを両方確認しないと
気づけないバグになっていた。

**修正**: `--years`引数を(渡されても)完全に無視する設計に変更し、常に`START_DATE`
固定を使うようにした。降雨と同じ堅牢さに揃えた。ワークフロー側からも`--years 10`を
削除した(実害はなくなったが、混乱を避けるため)。

```python
if args.years is not None:
    print(f"[fetch_typhoons] 警告: --years {args.years} が指定されましたが、"
          f"この引数は無視されます...")
```

### 2. ドキュメントの誤記2件

- **update-rainfallのtimeout**: PPTXに「120分設定」と記載されていたが、実際の
  ワークフローは`timeout-minutes: 300`(300分)。誤記を修正した。
- **update-lightningジョブの記載漏れ**: PPTX(p.5)のジョブ一覧に`update-lightning`が
  丸ごと欠落していた(地震・台風・elevation・floods・rainfall・aqueductの6つのみ
  記載され、雷が抜けていた)。新規に行を追加した。

### 3. 安全策の追加(fetch_typhoons.py)

取得・パースの途中で失敗した場合に本番ファイルを壊さないよう、一時ファイルに
書き切ってから`os.replace()`でリネームする方式に変更した。

```python
tmp_path = args.out + ".tmp"
with open(tmp_path, "w", encoding="utf-8") as f:
    json.dump(geojson, f, ensure_ascii=False, indent=2)
os.replace(tmp_path, args.out)
```

### 教訓

**スクリプト単体の修正だけでなく、それを実際に呼び出すワークフローファイルも
セットで確認しないと、修正が「見た目上は完了しているが実際には発動していない」
状態になりうる**、という教訓が今回得られた。今後、スクリプトの引数仕様を変える
修正を行う際は、呼び出し元(update-data.yml)も必ず一緒に確認する。
